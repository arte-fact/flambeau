# P2.9b-i2-F throughput cert — Qwen3.6-27B / pp2tp2 / batched-decode

**Date**: 2026-05-04
**Model**: Qwen3.6-27B-Q4_1 (qwen35moe arch, hybrid GDN + full-attn + dense FFN)
**Topology**: pp2tp2 — `--devices hip:0,2,1,3 --pp-size 2 --tp-size 2`
**Build**: post-#275 fix (commit 3e6b645)

## Result: 1.0× speedup at N=4 — gate FAILED, blocked by per-slot ceiling

| metric                          | value      |
|---------------------------------|-----------:|
| 4 sequential 128-tok generations| **20.95 s**|
| 4 concurrent 128-tok (N=4)      | **21.34 s**|
| speedup                         | **0.98×**  |
| target gate                     | ≥ 3.0×     |

Output: all 4 concurrent replies bit-identical (md5 match) and coherent;
correctness post-#275 is solid across N=2, N=4 greedy and chat-sampler
(temp=0.7, top_p=0.9, 4 distinct coherent responses).

## Root cause: per-slot GDN + full-attn loops in hybrid driver

`forward_decode_batched_hybrid` aggregates N slots, but inside the per-layer
rank loop:
- **GDN layers** call `forward_gdn_decode_tp` once per slot (n=N sequential
  state-step kernels with shared rank-level scratch).
- **Full-attn layers** call `forward_full_attn_layer_decode_batched_tp` which
  internally still loops per-slot for KV append + flash-attn (Q/K/V proj
  is batched at the layer entry).

Per-step wall time on hybrid scales ~linearly with N because the GDN /
attention compute is N × single-slot, not 1 × batched-N. The batched
matmul savings (Q/K/V proj, gate+up, FFN/MoE) recover some host-side
overhead but cannot reach 3× while the recurrent + attention floor is
N×.

llama.cpp / vLLM literature (cited in `doc/ROADMAP-V1-QWEN36-GFX906.md`)
agrees: continuous batching's headroom on hybrid GDN models requires
either fused batched-attention (single launch handles N (Q, KV) pairs)
or batched GDN state-step. Both are V2+ kernel work.

## What this cert validates (despite gate fail)

1. ✅ **Correctness** at N=2 / N=4 / pp2tp2 (post-#275): bit-identical
   output across concurrent dispatch, no garbling.
2. ✅ **Sampler correctness** at temp=0.7 / top_p=0.9 / N=4: 4 distinct
   coherent responses, no degeneracy.
3. ✅ **Larger prompt (365 prompt-tokens)** N=2: bit-identical concurrent
   output, coherent code-review answer.
4. ✅ **Default off / opt-in clean**: `FLAMBEAU_BATCHED_DECODE=1` +
   `FLAMBEAU_INFLIGHT_SLOTS=N` engages the path; default off reverts to
   legacy single-slot dispatch.

## Path to ≥ 3.0×

Tracked separately:
- **#266 P2.9b-i2-E** — batched-attention decode kernel (single launch,
  N Q-rows × per-slot KV). Estimated win: 1.5× from attention alone.
- **batched GDN** (no task yet) — fused N-slot state-step kernel sharing
  the conv1d / rmsnorm / qkv launches. Estimated win: 1.5–2× when
  combined with batched-attention.

Combined (#266 + batched GDN) likely to clear the 3× bar on hybrid.
Pure-PP and pure-TP topologies (no GDN, dense FFN) already gain ~1.18–1.21×
from current scheduler; closing those to 3× also wants batched attention.

## Reproduce

```bash
FLAMBEAU_BATCHED_DECODE=1 FLAMBEAU_INFLIGHT_SLOTS=4 \
  ./target/release/flambeau serve \
  --model /artefact/models/Qwen3.6-27B-Q4_1.gguf \
  --devices hip:0,2,1,3 --mesh-mode pp+tp --pp-size 2 --tp-size 2 \
  --port 8080
```

Then 4 concurrent vs 4 sequential `/v1/chat/completions` with
`temperature=0`, `max_tokens=128`. Wall difference is the batching
overhead (GDN/attn ceiling); correctness is bit-identical post-#275.
