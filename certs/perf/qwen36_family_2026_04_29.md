# Qwen3.6 family bench — long-prompt + long-response — 2026-04-29

Live-server bench across the Qwen3.6 model family on 4× MI50 PCIe / 100 W cap
/ ROCm 7.1.1, after the **TP-4d-i3 GDN K/Q replicated fix + `peer_copy_via_host`
HtoD-race fix** landed (Qwen3.6-35B-A3B / qwen35moe is now usable on TP2 and
pp2tp2 — previously gibberish).

Sampling `temp=0.7 top_p=0.9 seed=42`, prompt ≈ 653 tokens (~1500 chars),
`max_tokens=512`. Each model loaded fresh via `flambeau serve`, request issued
via curl, TTFT extracted from server `tracing` log.

## Headlines

### Qwen3.6-35B-A3B (qwen35moe MoE, 38 GB at Q8_K_XL, 20 GB at Q4_0)

- **TP2 is fastest**: **36 tok/s decode / 1034 tok/s prefill** on Q4_0.
  Confirms the MTP-5f / topology-compare finding that TP2 wins for MoE on this
  rig; matches the 33.6 tok/s reported in `qwen_family_long_prompt_2026_04_29.md`
  for pp4 (here 32.5 — within ±5% noise).
- **pp2tp2 NOW WORKS** (33.5 tok/s decode, 1005 tok/s prefill). Newly unblocked
  this session by the rep_outer GDN K/Q replicated fix. Slightly behind TP2
  because of cross-stage host-bounce hand-off + shared bounce-buffer HtoD sync.
- **PP4** (32.5) is consistent with the prior cert. UD-Q4_K_S (33.9) and
  UD-Q8_K_XL (32.2) are basically the same wall — A3B's working-set bandwidth
  dominates, quant only modulates lightly.

### Qwen3.6-27B (qwen35 dense, 16–35 GB)

- **pp2tp2 is fastest at Q4_0/Q4_1** (~21.2 tok/s decode / 309 tok/s prefill).
  Slightly above TP2 and PP4. **Q4_0 = Q4_1 within noise** here.
- **TP2 is close** (20.7 / 316). When 27B fits cleanly on 2 cards (Q4_*), TP2
  is a fine choice with half the device count.
- **PP4 lags both** (16.4 / 183 on Q4_1) — pipeline-parallel bubbles + per-stage
  PCIe peer-copy for dense forward path with no async overlap.
- **Q8_0** (15.1) and **UD-Q8_K_XL** (13.7) are HBM-bandwidth-bound; ~2× weight
  bytes vs Q4 buys ~30% slowdown (matches the qwen-family cert).
- **UD-Q6_K_XL is the slowest** (14.3 decode, **35 prefill**). The mixed-quant
  Q6_K rows in this UD ("Unsloth Dynamic") variant don't have a 4-warp MMQ
  prefill kernel on gfx906 — falls back to MMVQ at L=128, killing prefill
  throughput.

## Topology recommendation matrix (Qwen3.6 family on this rig)

| model | shipping topology | reason |
|---|---|---|
| Qwen3.6-35B-A3B Q4_0 | **TP2 (hip:0,1)** | fastest decode + prefill, MoE working-set fits on 2× 16 GB |
| Qwen3.6-35B-A3B Q4_K_S | pp4 | TP2 not measured; pp4 33.9 t/s is within noise of TP2 |
| Qwen3.6-35B-A3B Q8_K_XL | pp4 | 38 GB doesn't fit pp2 / TP2 |
| Qwen3.6-27B Q4_0 / Q4_1 | **pp2tp2 (hip:0,2,1,3)** | fastest 27B config (~21 t/s decode); TP2 nearly tied |
| Qwen3.6-27B Q8_0 / UD-Q8_K_XL | pp4 | 28+ GB doesn't fit pp2 / TP2 |
| Qwen3.6-27B UD-Q6_K_XL | avoid for prefill-heavy chat | missing 4-warp MMQ for Q6_K rows |

## Caveats

- ctx capped to 8192 (4096 for the largest at Q8_*) by KV-cache memory budget.
- Long-context decode rates here (~1500–2700 cumulative position) are slower
  than synthetic L=64 microbenches in V2.30.a (53.5 t/s 35B-A3B); KV walks
  scale linearly with position. This cert is the realistic chat-workload
  number.
- ±5% run-to-run variance on decode from kernel-launch jitter + thermal at
  100 W cap. Each row is a single run.
- The qwen35moe TP2/pp2tp2 results are all post-fix; pre-fix they were
  unusable (gibberish from token 2 onwards).
