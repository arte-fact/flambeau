# 1F1B-decode at PP=4/N=4 on Qwen3.6-27B-Q4_1 — null finding

**Date:** 2026-05-04
**Rig:** 4× MI50 (gfx906) PCIe 3.0 x16, ROCm 7.1.1
**Model:** Qwen3.6-27B-Q4_1 (qwen35moe — hybrid GDN+full-attn+MoE)
**Topology:** PP=4 / TP=1
**Task #:** #300 / #301
**Commits:** this branch (forward_decode_1f1b_hybrid + routes wiring)

## TL;DR

`forward_decode_1f1b_hybrid` is correct (md5-bit-identical across all 4
slots, output coherent) and ships behind `FLAMBEAU_DECODE_1F1B=1`,
**but it does not deliver the projected 2.29× speedup at decode**.
Wall time at PP=4/N=4 is ~26 s — same as both slot-major
`forward_decode_pipelined_hybrid` (#290/#294) and the unpipelined
`forward_decode_batched_hybrid` (#262 family).

Decode is HBM-bound on this hybrid arch; 1F1B is a compute-bound
pattern. The lever was wrong-targeted — see "Diagnosis" below.

## What 1F1B does (recap)

Stage-major timestep loop. For PP=k stages and N microbatches:
- timesteps = N + k − 1
- at tick t, each stage s in 0..k processes slot (t − s) if in range
- ceiling speedup = k² / (2k − 1) → 2.29× at PP=4/N=4

Vs. slot-major pipelined (`forward_decode_pipelined_hybrid`):
- one slot walks all stages sequentially before next slot starts
- only one rank busy per tick → ceiling ≈ 1.0× (no fill)

## Measurement

Test: 4 concurrent `/v1/completions` requests with greedy decoding,
each generating 64 tokens. Continuous-batching scheduler routes all 4
through `forward_decode_1f1b_hybrid` per step.

Setup:
```
FLAMBEAU_BATCHED_DECODE=1
FLAMBEAU_INFLIGHT_SLOTS=4
FLAMBEAU_DECODE_1F1B=1
```

| Mode                                    | Wall (s) | Ratio vs serial |
|-----------------------------------------|---------:|----------------:|
| 4 sequential                            |    ~26   |        1.00×    |
| Batched-decode (#262, no pipelining)    |    ~26   |        1.00×    |
| Slot-major pipelined (#290)             |    ~26   |        1.00×    |
| **1F1B (#298)**                         |  **~26** |    **1.00×**    |

All 4 outputs bit-identical (md5 b6eb0684...) across modes; decode
quality unchanged. The lever delivers 0× speedup despite the host
issuing all 4 stages' work at every steady-state tick.

## Diagnosis: decode is HBM-bound

At n_tokens=1, a single slot's stage = "stream this stage's weights
through HBM once for one query token." The aggregate HBM bandwidth on
4× MI50 PCIe is ~4 TB/s (1 TB/s × 4 cards), but each stage owns ~25 %
of the model weights — so stage k's weight-stream is independent
of the others. The four stages **could** stream their weight-strips
concurrently (different HBMs).

So why no speedup? The 1F1B host loop enqueues kernels on four
different `sub_cluster` streams (one per stage). HIP **does** dispatch
those concurrently. But:

1. **Each stage's per-slot work at n_tokens=1 is so HBM-bound and so
   tiny (~6.4 ms / slot / stage on 27B) that the per-tick host
   enqueueing latency (~100 µs/stage × 4 = 400 µs) is non-trivial
   relative to the kernel launches.**
2. **The slot-major variant (#290) already overlaps inter-stage
   peer-copy with stage compute via async bridge events.** Its only
   "wasted" time is the ramp-up/ramp-down bubble, which is identical
   in 1F1B (n_stages − 1 ramp ticks each side).
3. **Batched-decode at N=4 already amortizes HBM via n_tokens=N.**
   Each layer reads the weight strip ONCE for all 4 slots' work — no
   stage replication, no peer-copy, just tile-scaled GEMV. This is
   the dominant lever, and the slot-major / 1F1B variants give it up
   to swap N=1 over n_stages stages for N=4 in one stage.

The math: at PP=4, slot-major and 1F1B both amortize a per-stage
weight-strip read across N slots **on the same stage's stream**, but
they spend 4× the host issue cost vs. one batched call. 1F1B's only
delta vs. slot-major is host issue order — kernel-level it's
identical.

## When 1F1B *does* help (preserved for future use)

- **Prefill at long-prompt + multiple ubatches**: this is the V2.25.h
  win at PP=4/L=8192. Prefill is compute-bound (large M GEMM); 1F1B
  fills the per-stage idle gap.
- **Single-slot decode on >2 ranks if attention is the bottleneck**:
  e.g. dense attention + KV-quant where the per-stage weight-stream
  is much smaller than per-slot KV-stream. Not our hybrid case.
- **Pure dense FFN + MoE without GDN**: GDN's per-slot recurrent
  state-step is sequential on one stream regardless of host order.

`forward_decode_1f1b_hybrid` stays in-tree as opt-in
(`FLAMBEAU_DECODE_1F1B=1`) for those cases. Default off.

## What this means for the 3× gate

Per the v2 topology bench
(`certs/perf/topology_compare/qwen36_27b_topo_x_mode_pp1024_2026_05_04.md`),
PP=4 batched-decode at 4 concurrent users is 1.34× wall vs serial.
Slot-major pipelined (#290) and 1F1B (#298) keep that 1.34× — they
do not regress, they do not advance.

The 3× gate is **not closeable on PP=4 with PP-only re-pipelining**.

The remaining lever pointed at by the v2 cert (GPU% mean 25 % at PP=4
/ 44 % at TP=2 / 46 % at pp2tp2 — 50–75 % silicon idle) is **Lever 1
(Sarathi mixed prefill+decode batching)**:

- prefill chunk drives tensor cores (compute-bound)
- decodes drive HBM (bandwidth-bound)
- both sub-systems saturate in the same forward pass

This is the right shape for filling the silicon gap on a hybrid
GDN+attn+MoE workload where pure-decode batches are HBM-bound. It
applies across all topologies (TP/PP/hybrid), not just PP.

Recommendation: pivot to Lever 1 (#302–#308). Lever 2 (1F1B) is shipped
as opt-in but not on the critical path.
