# Flash-tile-Q8 prefill — Q8 wins F16 at 24k ctx

- **Model:** Qwen3.6-27B-Q4_0
- **Topology:** hybrid pp2tp2 (4× MI50, gfx906)
- **Date:** 2026-05-08
- **Workload:** 24,158-token prompt + 64-token greedy decode
- **Build:** flash-tile-Q8 (commit FT1)

## Headline

| metric | F16 | Q8 (post-flash-tile) | ratio |
|---|---:|---:|---:|
| **prefill (server-side TTFT)** | 129,825 ms | **128,731 ms** | **1.008× (Q8 +0.8%)** |
| **decode ms/tok** at n_kv ≈ 24k | 56.6 | **46.6** | **1.21× (Q8 +21%)** |
| **total wall** (prefill + 64-tok decode) | 134,664 ms | **131,718 ms** | **1.022× (Q8 +2.2%)** |

**Q8 KV at 24k context now strictly wins** — both prefill and decode.
The pre-flash-tile prefill regression (0.90× F16) is closed; Q8 now
matches F16 prefill within 1%, while preserving the 21% decode win.

Total-wall savings widen with longer decode tails — each decode token
saves 9.9 ms over F16, so a 1000-token response saves 13 s vs F16
on top of the 1 s prefill match.

## What flash-tile-Q8 does differently from the Q8 oracle prefill

Mirrors the F16 flash-tile kernel exactly except for the cooperative
LDS load:

| | oracle Q8 (pre this commit) | flash-tile Q8 (this commit) |
|---|---|---|
| grid | (n_q_tokens, n_heads_q) | (n_q_tokens / BR, n_heads_q) where BR = 4 or 8 |
| block | head_dim/4 (= 64 at d=256), 1 wave | (64, BR) = 256 or 512 threads |
| LDS K/V tile | none (each thread reads K/V from HBM per-token) | BC × D F32 floats, cooperatively loaded once per chunk |
| Q rows per block | 1 | BR (4 or 8 — share the K/V tile) |
| K/V re-reads | each Q row re-reads all K/V from HBM | each K/V chunk loaded ONCE, reused by BR Q rows |
| score-path math | dp4a int8 | F32 mul-add (LDS already F32) |
| HBM K traffic | n_q × n_k_chunks × head_dim bytes | n_q/BR × n_k_chunks × head_dim bytes (BR× reduction) |

The win is HBM K traffic reduction (BR=8× at d=256) from cooperative
LDS reuse, not from the score-path math itself. dp4a in the score
path was a wash here because each warp already does a F32 reduction
across 64 lanes per Q·K row — fast enough that the Q→Q8_1 quantize
overhead would dominate at small BC. The F16-equivalent flash-tile
math runs in F32 from LDS and is already efficient.

## Correctness

Coherent essay output on the canonical scheduler prompt + bit-different
hash vs the oracle Q8 path (`0e02…101a8` vs `5fcf…b27785`). The hash
divergence is **expected and analogous to F16 oracle vs F16 flash-tile**:
both Q8 kernels are mathematically valid; FP rounding order in the
tile-level online-softmax rescaling differs from the per-token oracle
softmax, and the difference compounds through 32+ layers of greedy
decode. Same rounding-order sensitivity exists in the F16 path
between its oracle and flash-tile kernels.

A standalone parity microbench (Q8 oracle vs Q8 flash-tile at fixed
n_q × n_k, max-abs delta in F16 outputs) is filed as a follow-up
but not on the perf-cert critical path — coherence is verified.

  module registered.

## Out of scope

- **Standalone parity microbench** Q8 oracle vs Q8 flash-tile at the
  kernel level (max-abs delta in F16 outputs). End-to-end coherence
  is verified; absolute parity within Q8 quant noise is the next
  follow-up if any user reports quality regressions.
- **dp4a in the flash-tile score loop** — the F32 LDS path already runs
  efficiently; switching to int8 LDS + dp4a would save HBM dequant work
  but doesn't help HBM K traffic (already minimised by the BR reuse).
  Defer until V is also INT8 (the INT-FlashAttention pattern).
- **Multi-slot batched-decode Q8** — `tp.rs:2760` bail still rejects
  Q8 in the continuous-batching driver. Single-request Q8 wins
  everywhere; multi-slot Q8 is a separate task.
