## Why the matmul-batched stages don't deliver a 4× win

`crates/ops/src/hip/qmatmul.rs::qmatmul` at small m:

```rust
if dtype_weight == QDtype::Q5_1
    || (dtype_weight == QDtype::Q4_0 && m < 32)
    || (dtype_weight == QDtype::Q5_0 && m < 32)
{
    // Row-by-row MMVQ: N × mmvq_simple_launch
    for i in 0..m {
        mmvq_simple_launch(weights, act + i*…, dst + i*…, …)
    }
    return Ok(());
}
```

For Q4_0/Q5_0/Q5_1 below m=32, dispatch falls through to row-by-row MMVQ.
The Q4_1 path also routes through `dispatch_qmatmul`, which has no
true-batched MMVQ kernel for small m — it picks an MMVQ recipe and loops.

So when my `forward_gdn_decode_batched_tp` calls `qmatmul(m=4, …)` in
Stages B/C/F, the kernel **launches 4 separate MMVQ kernels under the
hood**. Each launch reads the full weight tile from HBM. Total HBM
bandwidth is the same as 4×single-slot dispatch — no amortization of
weight reads across the 4 activation rows.

The launch-count savings are also marginal: 4× MMVQ in qmatmul vs 4×
fused-mmvq in `forward_gdn_decode_tp` is a wash; the `forward_gdn_*`
inner ops (conv1d + state-step + ssm_norm + …) still loop per slot too.

Stages A and E DO win (rmsnorm and swiglu over n_tokens=N batch
trivially in their kernels), but those are < 5 % of GDN wall time.
Net: ~3 % wall improvement over the no-batched fallback.

The structural ceiling at hybrid throughput on small-N decode is
**weight-read amortization in MMVQ**, not the per-slot loop overhead
itself.

## What this cert validates

- **Correctness**: Batched-GDN + per-slot conv1d/state-step inner loops
  produce output md5-identical-within-batch on Qwen3.6-27B / pp2tp2 /
  N=2/4/8. N=1 fast path unchanged. Both `FLAMBEAU_GDN_NO_BATCHED=1`
  fallback and default batched paths produce coherent output.
- **The plumbing**: per-slot `&mut GdnLayerState` slice handling, new
  `gdn_decode_batched: Option<GdnPrefillScratch>` per-rank scratch field,
  dispatch wiring in `forward_decode_batched_hybrid`. All in place;
  ready for a future batched-MMVQ kernel to slot in without further
  caller changes.
- **The next-lever identification** (#288): batched-MMVQ kernels that
  mirror the #266 attention pattern — grid=(n_rows/tile, N),
  read-weights-once across N activation rows. Estimated to lift the
  combined cert from 1.03× → 2-3× on hybrid; further levers (memory
  layout, prefetch) reachable from there.

## Path to ≥ 3.0× on hybrid (revised)

1. **#288 batched-MMVQ kernels** (Q4_0, Q4_1, Q5_K, Q6_K — the dtypes
   used in Qwen3.6's GDN matmuls). Grid=(n_rows/r, N). Reads weight
   once, computes N output rows. Mirrors #266 attention pattern.
2. After #288, re-run this cert. If still under 3×, profile to identify
   the next ceiling (likely AR-residual host overhead or output-head
   per-slot loop).
