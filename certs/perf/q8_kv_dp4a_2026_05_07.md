# Q8 KV dp4a rewrite — kernel cert

- **Model:** Qwen3.6-27B-Q4_0
- **Topology:** hybrid pp2tp2 (4× MI50, gfx906)
- **Date:** 2026-05-07
- **Commits:** D1–D4 in this PR

## Headline

All three Q8 KV attention kernels (`attention_decode_q8_kv`,
`attention_decode_q8_kv_splitk`, `attention_prefill_q8_kv`) rewritten
to use `__builtin_amdgcn_sdot4` (gfx906 `v_dot4_i32_i8`, the dp4a
analogue) for the score loop. Q is quantised to Q8_0 in LDS once per
(q_token, q_head) block; K is read as packed int32; scalar
`K.d × Q.d` applied once per QK8_0 block (32 elements). V path stays
on FP16 dequant per element (Phase 2 / INT-FlashAttention-style PV in
INT8 is the V2 follow-up).

**End-to-end wall numbers (Qwen3.6-27B / pp2tp2 / 214-tok prompt + 80-tok decode):**

| arm | wall | hash |
|---|---:|---|
| F16 KV | 3.76 s | (different sampling path, not directly comparable bit-for-bit) |
| Q8 KV pre-dp4a (FP-dequant) | 3.72 s | `5fcf...` |
| **Q8 KV post-dp4a** | **3.71 s** | `5fcf...` (bit-identical) |

**Long-decode profile (short prompt + 400-tok decode, n_kv 25 → 425):**

| window | pre-dp4a | post-dp4a |
|---|---:|---:|
| 0..100 (single-pass) | 44.74 ms/tok | **37.68 ms/tok** (–15.7%) |
| 100..200 (single-pass) | 36.37 | 36.15 |
| 200..300 (split-K) | 39.03 | 35.59 |
| 300..400 (split-K) | 40.15 | 35.08 |
| **total wall** | **16072 ms** | **14460 ms (–10%)** |

Decode rate stays flat 35–37 ms/tok across n_kv = 25 → 425.

## What dp4a actually delivered

The kernel-level win is real: single-pass attention 0..100 ms/tok
window dropped 15.7%. That's the dp4a inner loop saving ~17× score-
path compute density over the FP-dequant version, exactly matching
the analysis in `doc/Q8_KV_DEQUANT_ANALYSIS.md`.

But the **overall wall** is barely moved. Why: this MoE workload
is *not* KV-bandwidth-bound. Per-decode-step HBM accounting on
Qwen3.6-27B-Q4_0 at ctx=300:

| component | bytes/step (approx) | share |
|---|---:|---:|
| MoE expert weights (Q4_0, 8/128 active experts) | ~5 GB | **99.8%** |
| F16 KV (32 full-attn layers × 256 head_dim × 2 bytes × 2 K+V × 300 ctx) | ~9.8 MB | 0.2% |

Halving KV bytes saves 0.1% of HBM traffic. The model is MoE-weight-
bound on decode, not KV-bound. Q8 KV's wall ceiling on this workload
is bounded by KV's tiny share of total HBM traffic — there is no
1.5× to be had on wall.

The win shows up only when:
- Context length is huge (KV bytes grow linearly with ctx; at 32K
  context, KV reads ≈ 1 GB and start to matter relative to weights).
- Memory pressure forces shorter ctx with F16 (Q8 fits 2× longer ctx
  in the same VRAM — that's the real production win, not throughput).
- Dense models (no MoE) where weights don't dominate.

## Correctness

Bit-identical output (SHA-256 = `5fcf53291435cf91e0797d09381b963ae08
357ee79010b78d2eda8718bb27785`) across:
- pre-dp4a Q8 single-pass + split-K + prefill kernels
- post-dp4a Q8 single-pass + split-K + prefill kernels
- the same prompt + greedy + seed=0 the previous Phase-3 batched-
  prefill cert used at commit `9960e44`.

Same hash means the dp4a path produces the SAME int-quantized
intermediate as the FP-dequant path at this prompt — modulo
rounding-order differences that didn't propagate through the model.

## Out of scope (V2 follow-ups)

- **INT8 PV path** (the +72% INT-FlashAttention extension) —
  quantize the post-softmax attention weights to Q8_1 per row, run
  PV via dp4a too. Today V is still per-element FP16 dequant. Worth
  doing on dense models or large-ctx workloads where attention has
  a larger share of wall.
- **Flash-tile-Q8 prefill** (BR=4/8 LDS-tiled equivalent of
  `attention_prefill_flash_tile_f16`). Today Q8 prefill uses the
  oracle (one block per (q_token, q_head)). Would close the
  prefill gap on very long prompts.
- **Better intra-warp dp4a packing** — the current kernel uses
  block = head_dim/4 which gives 1-wave blocks on head_dim=256.
  At low n_heads_q (TP-sharded ≤ 8) this caps occupancy at
  ~13% silicon. A multi-q-head-per-block variant would help, but
  the wall is bounded by MoE weights anyway on this workload.

## Conclusion

dp4a kernels are now structurally correct and fast at the
attention-call level (–15.7% on the single-pass decode-attention
window). Q8 KV ≤ F16 wall on every measured config (was the bar).
Beating F16 by a meaningful margin on Qwen3.6-27B is structurally
hard because KV is < 1% of per-decode-step HBM traffic on MoE
workloads. The win moves to long-context dense models or to
VRAM-fitting headroom, not to short-prompt throughput.

The full doc analysis is in `doc/Q8_KV_DEQUANT_ANALYSIS.md`.
