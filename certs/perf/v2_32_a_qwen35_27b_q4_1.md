# V2.32.a — Qwen3.5-27B-Q4_1 as the 27B shipping config (mi50grad-inspired)

## Motivation

`github.com/larkinwc/mi50grad` achieves 53.7 tok/s decode on
Qwen3.5-27B-**GPTQ-Int4** at TP=4 on 4× MI50 32 GB cards. Our
Qwen3.6-27B-**Q8_0** Mesh<4> PP peaks at 18.4 tok/s decode. Two
independent gaps:

1. **Quant**: Q8_0 is 2× the HBM traffic per weight vs Q4. 27B decode
   is largely per-token dense matmul bound.
2. **Topology**: mi50grad uses TP with kernel P2P via BAR1; we use PP
   with peer-copy-via-host. TP requires 32 GB per card (doesn't fit on
   our 16 GB cards) and kernel P2P allreduce changes the comms profile.

This cert picks the lowest-hanging change: **switch the 27B shipping
config from Qwen3.6-27B-Q8_0 to Qwen3.5-27B-Q4_1**.

The two models are structurally identical at the arch level (both
`qwen35` hybrid GDN + full-attn, 64 layers, n_heads=24, n_kv_heads=4,
head_dim=256, hidden=5120, feed_forward_length=17408, ssm_inner=6144).
Only the weights (training + quantisation) differ.

| L    | Qwen3.6-27B-Q8_0 | **Qwen3.5-27B-Q4_1** | Δ          |
|------|-----------------:|---------------------:|-----------:|
|  128 |              99 |                  177 | **+80 %**  |
|  512 |             160 |                  315 | **+97 %**  |
| 1024 |             230 |                  463 | **+101 %** |
| 2048 |             284 |                  561 | **+98 %**  |
| 4096 |             315 |                  559 | **+77 %**  |
| 8192 |             318 |              **566** | **+78 %**  |
| decode tg=64 |    18.4 |             **21.1** | **+15 %**  |

Total VRAM: 26.6 GiB (Q8_0) → 16.0 GiB (Q4_1). Still needs Mesh<4>
due to 262144-token KV cache context allocation, not weight footprint
(Q4_1 weights alone would fit 2 cards; scratch + KV bloats it).

## Q4_0 tested, losing variant

Q4_0 same model quant performs **worse** than Q4_1 on flambeau:

| L    | Q4_1 | Q4_0 |
|------|-----:|-----:|
|  512 |  315 |  123 |
| 1024 |  463 |  176 |
| 4096 |  559 |  243 |

Root cause: Q4_1 routes through `mmq_q4_1_4warp_lds` (V2.13-era
128-thread × 128×64 LDS-tiled MMQ — the current local optimum on
gfx906 per V2.29.e/V2.31.f). Q4_0 routes through
`qmatmul_q4_0_mmq_wave64_gfx906` (V2.28.a) — 64-thread wave64
variant with no LDS tiling, hence slower at the dense 27B shapes.

**Recommendation**: stick with Q4_1 as the 27B shipping quant.

## Path to 50 tok/s decode

With Q4_1 we're at 21 tok/s. The remaining 29 tok/s gap to 50 can only
be closed by:

1. **Speculative decoding** (n-gram / EAGLE) — mi50grad measured 54 %
   n-gram acceptance on real text, translating to ~1.5× effective
   decode. Projected: 21 → ~32 tok/s.
2. **Kernel register blocking** (mi50grad v7/v8) on Q4_1 MMVQ — their
   FP32-only accumulation + 2-4× register blocking delivered +3-6 %
   on standalone GEMV, +18 % on small-N attention projections.
3. **TP retopology** — would require refactor + 32 GB cards. Out of
   V1 scope per CLAUDE.md rig constraint.

**Shipped here**: the quant swap is a +15 % decode / +97 % prefill
win with **zero code changes** (arch already supported, kernels
already in place).
