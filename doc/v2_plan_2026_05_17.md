# v2 model implementation — plan (2026-05-17)

The two scaffolds (`crates/model-ops`, `crates/forward`) are in place.
This document is the concrete sequence to fill them in, migrate the
three current archs onto v2, and retire the existing `crates/blocks` +
`crates/models/{qwen3-moe, gemma4}` once v2 is at parity.

It is ordered. Each phase has a clear "done when" and a single
question that locks in before the next phase starts. The existing
implementation stays running the entire time and is the correctness
oracle for every parity test.

## Scope

In:
- `crates/model-ops/src/ops/` — leaf ops, one file per op, each with
  CPU reference + on-device parity test.
- `crates/forward/src/{pp,tp,hybrid}.rs` — three `ForwardCtx` impls
  composing model-ops leaves with topology-correct AR / peer-copy /
  handoff.
- `crates/models/{qwen35, qwen36-moe, gemma4}-v2/` — thin model
  crates writing one `forward_one_token<C: ForwardCtx>` and one
  `forward_prefill<C: ForwardCtx>` each.
- Server-side cutover: `crates/server/serve.rs` constructs v2 models +
  v2 ForwardCtx; old per-arch driver path retires.

Out:
- CUDA backend (later; v1 ships HIP only, same as the existing crates).
- Scheduler / batched-decode kernel changes (orthogonal).
- KV-cache type changes (Q8 KV, turbo quant — same shape as today).
- New features in old crates (gemma4 per-layer-embd, MoE prefill,
  Q8 KV). Those land in v2 where they cost ~200-500 LOC each.

## Decisions (locked 2026-05-17)

1. **Scratch lifetime in `ForwardCtx`: lifetime-tied `Tensor<'a, F16>`.**
   Returned tensors borrow from the ctx's per-layer scratch pool;
   valid until the ctx is next mutably borrowed. Most type-safe.
   If lifetime annotations virally cascade into model signatures
   during P3, **stop and revisit** rather than ship with `<'a, C:
   ForwardCtx>` everywhere.

2. **First model: qwen35 dense (Qwen3.5-9B-Q4_1).** Simplest existing
   arch: no MoE, no GDN, no per-layer-embd, no ISWA, no softcap.
   Already validated end-to-end against llama.cpp in the bench matrix.

3. **First topology: single-device.** Adds a fourth
   `SingleDeviceForwardCtx` (trivial, no rank loops, no AR) as the
   correctness pin before the topology dimension lands. P3 parity
   tests against existing `qwen3-moe/src/forward/single_device.rs`.

4. **Cutover threshold: parity + 1.0× perf (no regression).** Old
   crate is deleted when its v2 replacement:
   - passes every existing parity test (synthetic + real-GGUF),
   - **matches or beats** the old impl's throughput on every bench
     matrix cell (no regression accepted).
   No "keep around in case" grace period. Implication: each
   migrated model gets a perf-tuning sub-phase between functional
   parity and deletion. If v2 ships at 0.95× v1 it does NOT cut over;
   we tune until ≥ 1.0×.

5. **Gemma4 features (Q8 KV, MoE prefill, per-layer-embd, shared-KV
   tail) in OLD crate: no.** Each feature costs ~5-10× in old vs v2
   per the LOC ratio. Existing gemma4 (31B-Q4_0, 26B-A4B-Q8_0) is
   the production correctness oracle; missing features land cheap in
   v2's P8.

## Phases

### P0 — first op end-to-end (locks the leaf-op pattern)

**Goal.** One op (`rmsnorm_f16`) lands in `crates/model-ops/src/ops/`
with CPU reference + on-device parity test. Validates the file
layout, the `Tensor<T>` ergonomics, the test scaffold from
`testing.rs`, and the recipe in `crates/model-ops/CLAUDE.md`.

**Work.**
- `src/ops/rmsnorm.rs` containing:
  - CPU reference `cpu_rmsnorm_f16(input: &[f16], weight: &[f16], n_rows, hidden, eps) -> Vec<f32>`.
  - Device op `rmsnorm_f16(input, weight, output, n_rows, hidden, eps, ops) -> Result<()>`.
  - `#[cfg(test)] mod tests` with synthetic input (linspace,
    deterministic seed), n_rows=4, hidden=64.
- Re-export from `src/ops/mod.rs` and `src/lib.rs`.

**Done when.** `cargo test -p flambeau-model-ops --features hip` is
green on the rig. The test exercises a real device.

**Lock.** API shape of an op file. If anything feels wrong, revise
the recipe in `CLAUDE.md` here — not later when 20 ops are in.

**Effort.** 1-2 days.

### P1 — op vocabulary (model-ops bring-up)

**Goal.** Port the kernel-call surface qwen35 needs into model-ops as
leaf ops with parity tests.

**Work.** One file per op, every op shipped with its test. List:
- `rmsnorm_f16`, `rmsnorm_quant_q8_1`, `rmsnorm_f32`
- `add_f16`, `add_f32`
- `cast_f32_to_f16`, `cast_f16_to_f32`
- `scale_f16`
- `embed_lookup_f16`
- `rope_neox_f16` (gemma uses neox; qwen35 same)
- `quant_f32_to_q8_1`, `quant_f16_to_q8_1`
- `qmatmul_q4_1` (qwen35's dtype), `qmatmul_q4_0`, `qmatmul_q5_0`,
  `qmatmul_q5_1`, `qmatmul_q8_0` (cover the dense families upfront)
- `mmvq_simple_*` for the small-m decode path
- `kv_append_f16`
- `attn_decode_f16` (flash + splitk variants exposed as one op)
- `attn_prefill_f16`
- `gated_mlp_f16` (gate*silu(up) elementwise; the matmul half is qmatmul)
- `softmax_f32`
- `topk_softmax_f32` (the sampler kernel)

~20-22 ops. Each ~80-150 LOC including its test.

**Done when.** Every listed op has a passing test. The op vocabulary
covers qwen35's full forward + sample path.

**Effort.** 2-3 weeks. Can be parallelised across ops once the
pattern is locked.

### P2 — `SingleDeviceForwardCtx` + first composites

**Goal.** Bring up a fourth `ForwardCtx` impl that's trivial (no rank
loops, no AR, no peer-copy) and use it to drive composites end to
end. Adds the executor's "compose leaf ops" patterns without the
topology cost.

**Work.**
- New file `crates/forward/src/single_device.rs` with
  `SingleDeviceForwardCtx { device, ops, kv_caches, scratch, position, logits_host }`.
- Implement every method of `ForwardCtx` on it. Each method calls
  model-ops leaves directly; no AR / no peer-copy / no rank dimension.
- Decide scratch lifetime here (per "decisions to lock"). The whole
  composite layer commits to one shape.
- Parity test scaffolding: drive `SingleDeviceForwardCtx` from a
  tiny synthetic model and assert outputs match a hand-coded
  reference (still no real GGUF, still synthetic weights).

**Done when.** Every `ForwardCtx` trait method has a concrete impl on
`SingleDeviceForwardCtx`. A synthetic forward (embed → 2 layers →
output_head) under this ctx produces the expected tensor shapes and
runs without panic.

**Effort.** 1-2 weeks.

### P3 — qwen35-v2 single-device, parity against existing

**Goal.** First real model on the v2 stack. End-to-end forward
matches existing `qwen3-moe/src/forward/single_device.rs` on the same
GGUF.

**Work.**
- New crate `crates/models/qwen35-v2/` with:
  - `config.rs`, `names.rs`, `layout.rs` (copied from existing
    `qwen3-moe/src/{config,names,layout}.rs`; trim to the dense path,
    drop MoE / GDN / per-layer-embd fields).
  - `weights.rs` — `Qwen35Weights` struct holding `Tensor<F16>` /
    `Tensor<Q4_1>` etc. per role.
  - `upload.rs` — GGUF → device weights. Can call existing
    `flambeau-blocks::weight_roles::WeightUploader` — it's a leaf-
    level helper, not topology-aware, fine to reuse.
  - `forward.rs` — the ONE function:
    ```rust
    pub fn forward_one_token<C: ForwardCtx>(
        model: &Qwen35Weights,
        layout: &ModelLayout,
        ctx: &mut C,
        token: u32,
        position: usize,
    ) -> Result<u32>;
    ```
  - `prefill.rs` — same shape, multi-token.
- Parity test: load `Qwen3.5-9B-Q4_1.gguf` on hip:0, run 8 decode
  tokens through both `qwen3-moe::single_device::forward_one_token`
  and `qwen35-v2::forward_one_token<SingleDeviceForwardCtx>`. Bit-
  equal F16 outputs.

**Done when.** Parity test passes on real GGUF. `qwen35-v2/src/forward.rs`
is < 500 LOC.

**Lock.** The model crate's file layout, the upload pattern, the
weight-handle shape passed into composites. All future models follow
the same layout.

**Effort.** 2-3 weeks. The bulk is wiring weight roles + parity
debugging.

### P4 — `PpForwardCtx` end-to-end

**Goal.** Same qwen35-v2 forward function (unchanged) runs under
pipeline-parallel topology.

**Work.**
- Fill in `crates/forward/src/pp.rs` `todo!()`s. Implement
  `layer_range` to yield this rank's layers + trigger
  `peer_copy_via_host` at stage boundary on iterator drop / final
  yield.
- Per-request state struct: rank, n_ranks, layer_to_rank,
  `&mut [KvCache<F16Contig, HipDevice>]` slice for this rank's
  layers, scratch pool, position counter, host logits slot (last
  rank only).
- Parity test: same `Qwen3.5-9B-Q4_1` on `hip:0,1,2,3` PP4, 8 decode
  tokens, bit-equal to existing `qwen3-moe::forward::pp` impl.

**Done when.** Parity test passes. PP composite methods on
`ForwardCtx` are filled in.

**Effort.** 2 weeks.

### P5 — `TpForwardCtx` end-to-end

**Goal.** Same qwen35-v2 forward function runs under tensor-parallel
topology.

**Work.**
- Fill in `crates/forward/src/tp.rs`. The composites that involve
  row-parallel projections (`standard_attn`, `dense_ffn`) end with
  `tp_sum` AR; column-parallel projections shard their weights and
  feed local outputs into the AR.
- Per-request state: rank, n_ranks, BAR1 AR handle, per-rank
  TpRankCore (producer_done event), KV refs (local KV-head shard),
  scratch (local-width).
- Parity test: same model on `hip:0,1` TP2.

**Done when.** Parity passes. TP composite methods filled in.

**Effort.** 2 weeks.

### P6 — `HybridForwardCtx` end-to-end

**Goal.** Same qwen35-v2 forward function runs under pp+tp.

**Work.**
- Fill in `crates/forward/src/hybrid.rs`. Composites use per-stage
  sub-cluster AR (not the global one). `layer_range` yields stage
  layers + triggers handoff with **the stream-drain invariant** from
  project memory (`hipcluster_stream_handles`): drain both sub-
  cluster AND global-cluster default streams before peer_copy.
- Parity test: `Qwen3.5-9B-Q4_1` on `hip:0,2,1,3` pp2tp2.

**Done when.** Parity passes. All four ForwardCtx impls
(SingleDevice / Pp / Tp / Hybrid) green on qwen35.

**Lock.** ForwardCtx surface is now load-bearing. From here on,
adding a composite means touching all four impls; the scaffold's
discipline rules (`crates/forward/CLAUDE.md` rule 1) start to bite.

**Effort.** 2-3 weeks. Hybrid is the most complex because of the
stream-drain invariant and per-stage AR scoping.

### P7 — qwen36-moe-v2 (MoE composite)

**Goal.** Second model on v2. Adds MoE ops + the `moe_ffn` composite
to all four ForwardCtx impls.

**Work.**
- New leaf ops in model-ops: `topk_softmax_f32` (already in P1),
  `indexed_mmvq_q4_0_f16`, `combine_topk_f16` (or whatever the
  router/expert/combine vocabulary is on qwen3-moe). Same recipe —
  CPU reference + test per op.
- `moe_ffn` composite added to each ForwardCtx impl. PP / single-
  device: local MoE composer. TP / Hybrid: parallel-branch composer
  with shared-MLP partial + routed-MoE partial + F32 AR on partials
  (the F16 overflow fix from `gemma4_moe_f16_overflow` memory).
- New crate `crates/models/qwen36-moe-v2/`. Mostly a copy of qwen35-v2
  with MoE FFN branch + GDN attention.
- GDN is the wildcard — Qwen3-Coder-Next (qwen3next) has it. If
  qwen36-moe doesn't need GDN, defer it; if it does, lands here as
  ops + composite.

**Done when.** qwen36-moe-v2 parity on `Qwen3.6-27B-Q4_0` across all
four topologies (or three if pp2tp2 only fits the 35B-A3B variant —
match existing coverage).

**Effort.** 2-3 weeks. MoE composite is non-trivial; the rest is
copy-shape from P3.

### P8 — gemma4-v2 (per-layer-embd + ISWA + softcap + the missing features)

**Goal.** Third model. Also lands the gemma4 features that were never
implemented in old crate (per-layer side-channel embed for E2B/E4B,
shared-KV tail, MoE prefill, Q8 KV).

**Work.**
- New leaf ops in model-ops for gemma4 specifics:
  - `apply_logit_softcap_f32`
  - `apply_layer_output_scale_f16`
  - `per_layer_embed_lookup_f16` (E2B / E4B)
  - `attn_decode_f16` with window mask (ISWA)
- gemma4 composite tweaks: `standard_attn`'s output_proj F32 path on
  full-attn + head_dim≥256 + Q8 (`gemma4_attn_output_proj_f16_saturate`),
  `moe_ffn`'s F32 cascade (`gemma4_moe_f16_overflow`), `embed`'s
  `sqrt(n_embd)` scale.
- New crate `crates/models/gemma4-v2/`. Forward function shape same
  as qwen35-v2; the only divergence is the gemma4-specific
  composites and the per-layer-embd lookup at layer entry.
- Add the missing features as op compositions:
  - **Q8 KV.** New `KvCache<Q8Contig>` type + composite branch.
    ~200-300 LOC.
  - **MoE prefill.** Same MoE composer as decode but batched over
    n_tokens. Mostly reuses ops; ~150 LOC.
  - **Shared-KV tail.** Layer iteration honors `kv_share_src` —
    tail layer reads from another layer's KV slot in same stage.
    ~50 LOC in `layer_range` + composite arg handling.
  - **Per-layer-embd.** E2B / E4B side-channel; `embed` composite
    branch + new leaf op. ~200 LOC.

**Done when.** gemma4-v2 parity on all five GGUFs we test today
(E4B-Q4_0, 31B-Q4_0, 31B-Q8_0, 26B-A4B-Q8_0, 26B-A4B-UD-Q8_K_XL)
across all four topologies. Missing features (Q8 KV, MoE prefill,
shared-KV, per-layer-embd) functional end-to-end.

**Effort.** 3-4 weeks.

### P9 — server cutover + delete old

**Goal.** `crates/server/src/serve.rs` constructs v2 models exclusively.
Old crates deleted.

**Pre-req (per locked cutover decision).** v2 throughput is **≥ 1.0×**
v1 on every bench matrix cell for the model being cut over. If any
cell regresses, P9 doesn't start for that model — go back and tune.
Likely tune-points: trait-method monomorphisation (verify with
microbench; if cold, fall back to `enum ForwardCtxKind` per the risk
section), scratch pool reuse patterns, AR + handoff scheduling
overhead vs the old `LayerComposerTp` open-coded path.

**Work.**
- Replace `Gemma4Driver` / `Qwen3MoEShardedModel` constructions in
  `serve.rs` with the v2 equivalents.
- Replace `gemma4_handle.rs` / `model_handle.rs` / `qwen3moe_handle.rs`
  with v2-bound versions. The `Model` / `Session` trait surface in
  `flambeau-server-core` likely simplifies — v2 doesn't need
  `forward_decode_batched` overrides per arch because the executor
  doesn't aggregate at that level. Re-evaluate the trait.
- Delete `crates/blocks/` (or the parts no longer used; some
  primitives like `BarP2pAllReduce` are kernel-level and stay).
- Delete `crates/models/qwen3-moe/` and `crates/models/gemma4/`.
- Re-run the full bench matrix as the final no-regression gate.

**Done when.** Old crates removed from `Cargo.toml` workspace. Server
boots, all parity tests in `crates/models/*-v2/tests/` are the only
ones (no v1 tests left to maintain). Bench matrix is ≥ 1.0× v1 on
every cell.

**Effort.** 3-5 days for the wiring + delete; perf-tuning effort
captured in the per-model phases (P3 / P7 / P8) ahead of P9.

## Risks / known unknowns

1. **Scratch lifetime explodes the model signatures.** If
   `Tensor<'a, F16>` viralises the lifetime into `<'a, C: ForwardCtx>`
   everywhere, fall back to option 3 (caller-passed buffers) early —
   before P3 ships qwen35-v2's forward.
2. **GDN doesn't fit the composite pattern.** Gated Delta Net (qwen3-
   coder-next, possibly qwen36) has stateful pseudo-attention. If
   `moe_ffn` + `standard_attn` aren't the right composites for it,
   add a `gdn_block` composite — but only after walking through
   what the model code actually needs to write.
3. **Hybrid stream-drain regresses on real hardware.** The fix in
   `hipcluster_stream_handles` (cc68970) is non-obvious. P6 needs to
   bake it into `layer_range`'s handoff path with explicit test
   coverage; missing it = nondeterministic gibberish on 26B-A4B
   pp2tp2.
4. **v2's perf is below v1 because the executor adds method-call
   overhead.** Generic `<C: ForwardCtx>` should monomorphise away
   the trait calls; verify with a microbench before P9. If
   monomorphisation underperforms, the fallback is `enum
   ForwardCtxKind { Pp(..), Tp(..), Hybrid(..) }` with explicit
   match in each composite — uglier but no virtual call.
5. **Estimates are optimistic by 30-50% (typical).** If the project
   is over budget by P3, stop and re-estimate. Don't compound.

## What NOT to do

- Don't add a composite to `ForwardCtx` that only one impl can
  implement. The discipline rule in `crates/forward/CLAUDE.md` (#1)
  exists for this exact failure mode.
- Don't bypass model-ops to call kernels directly from the executor.
- Don't add `Stage` / `Driver` / `Session` types in either new crate.
  Per-request state is per-impl struct fields, not parallel types.
- Don't preserve a "grace period" for old crates. Once a model's v2
  passes parity, delete its v1.
- Don't land gemma4 features in the OLD crate while v2 is in flight.
  That's throwaway work at 5-10× the cost.
- Don't add CUDA paths now. Backend split is a later phase; v1 is
  HIP-only.
