# Q8 vs F16 KV at 24k context — long-ctx perf cert

- **Model:** Qwen3.6-27B-Q4_0 (GGUF)
- **Topology:** hybrid pp2tp2 (4× MI50, gfx906)
- **Date:** 2026-05-08
- **Workload:** 24,158-token prompt + 64-token greedy decode
  (`scripts/bench/q8_vs_f16_32k.py`)
- **Build:** post-D4 commit `cb8760f` (dp4a score path)

## Headline

| metric | F16 | Q8 | ratio |
|---|---:|---:|---:|
| **prefill (server-side TTFT)** | 129,825 ms | 143,867 ms | 0.90× (Q8 −10.8%) |
| **decode ms/tok** at n_kv ≈ 24k | **56.6** | **46.7** | **1.21× (Q8 +17.5%)** |
| total wall (prefill + 64-tok decode) | 133,450 ms | 146,856 ms | 0.91× |

**Q8 decode is 21% faster than F16 at 24k context** — exactly the theory
(Q8 reads ~half the KV bytes during attention; at this context KV
finally outweighs MoE expert reads in HBM accounting).

The prefill regression comes from a missing kernel, not from Q8
itself: F16 prefill uses the BR=8 LDS-tiled `attention_prefill_flash_tile_f16`
(super-efficient cooperative load), while Q8 still uses the oracle
`attention_prefill_q8_kv` (one block per `(q_token, q_head)`, no tile
reuse). Writing `attention_prefill_flash_tile_q8_kv` is V2 follow-up
already filed in `doc/Q8_KV_DEQUANT_ANALYSIS.md`.

## Per-step HBM accounting (the prediction worked)

The Phase-4 cert (`q8_kv_dp4a_2026_05_07.md`) noted: at ctx=300, KV is
~0.2% of per-step HBM traffic — so Q8 ≈ F16 wall. At ctx=24k:

| component | bytes/step | share |
|---|---:|---:|
| MoE expert weights (Q4_0, 8/128 active experts) | ~5 GB | ~88% |
| F16 KV (16 full-attn × 256 head_dim × 2 bytes × 2 K+V × 24158 ctx) | ~395 MB / GPU = ~395 MB amortized | ~7% |
| (other layers, GDN state, activations) | ~280 MB | ~5% |

Q8 halves the KV portion (~395 → ~210 MB), saving ~3-4% of total
per-step HBM traffic. Compounding across 64 decode steps and the dp4a
score-path compute saving (which removes the per-element FP16-cast bottleneck —
see `doc/Q8_KV_DEQUANT_ANALYSIS.md`), the 21% decode speedup is
slightly above the pure HBM-bytes prediction. This is consistent with
the dp4a kernel being now compute-light enough that the kernel runs
HBM-bound at this ctx, where pre-dp4a it was compute-bound.

## When does Q8 win on TOTAL wall?

Each decoded token saves `56.6 − 46.7 = 9.9 ms` vs F16. The Q8 prefill
regression is `+14,042 ms`. Decode count to break even:
`14,042 / 9.9 ≈ 1418 tokens`.

So Q8 wins on total wall once `n_decode ≥ ~1500` tokens. Typical chat
completion tops out around 200-500 decoded tokens, where F16 still
wins on wall by 5-10%. Long-form generation (essays, code, > 2000-tok
responses) flips the outcome — Q8 wins net.

## Production guidance (until flash-tile-Q8 lands)

- **Default to F16 KV for chat/conversational workloads** (short
  responses, 200-500 decode tokens). Until flash-tile-Q8 prefill
  lands, Q8 prefill on long prompts is structurally slower and
  dominates the wall on chat.
- **Use Q8 KV when context > 16k AND decode > ~1500 tokens** —
  long-form generation, agent loops, batch summarisation. The decode
  speedup compounds over enough tokens to overcome the prefill
  regression and net-win.
- **Always use Q8 KV when VRAM-bound** — Q8 fits ~2× the context in
  the same VRAM (`0.54 GB → 0.29 GB` per GPU at 32k ctx). For
  workloads where ctx is the constraint, the wall question is moot —
  F16 doesn't run at all.

## What this DOES NOT show

- **Bit-identical output verification at 24k ctx is not in this cert** —
  the bench harness only captures wall + completion_tokens, not
  hashes. The Phase-4 dp4a cert (`q8_kv_dp4a_2026_05_07.md`) verified
  bit-identical output up to ~300 ctx. At 24k the dp4a path runs the
  same kernel many more times; correctness should still hold (the
  kernel has no ctx-length-dependent path), but a parity test at this
  scale is filed as a follow-up.
- **Multi-batch decode** — single request only. Multi-slot decode at
  24k ctx would need P2.9b-Q8 (`tp.rs:2760` bail still rejects Q8
  in batched decode driver).

## V2 follow-ups (in priority order)

1. **`attention_prefill_flash_tile_q8_kv` kernel** — port BR=8 LDS-tiled
   F16 flash-tile to Q8 KV. Most-impactful next step: closes the 14 s
   prefill regression at 24k, which makes Q8 net-win on every long-ctx
   workload (not just decode-heavy). Probably ~200 LOC kernel mirroring
   the F16 flash-tile structure with on-the-fly Q8 dequant in the K
   tile and dp4a score reduction.
2. **Multi-slot batched-decode Q8** — drop the bail at `tp.rs:2760` and
   wire the layout-generic decode through the batched-decode driver.
3. **Long-ctx parity test** — confirm Q8 dp4a output stays bit-identical
   to F16 at 24k+ ctx (or quantify the divergence within Q8 quant noise).
4. **INT8 PV path** (the +72% INT-FlashAttention extension) — only
   moves the needle on dense models, not Qwen3.6-MoE.
